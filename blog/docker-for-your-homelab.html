Docker for Your Homelab: Self-Hosting Without the Fear

August 2, 2026 · Heston Norcott, E.I.

The old way of self-hosting went like this: install a service directly on the server, then install the next one, and the next — each one demanding its own runtime, its own database, its own idea of which Python version should win. Six months later the machine is a museum of half-remembered installs, one upgrade breaks two unrelated services, and rebuilding the whole box is a weekend you don't want.

Docker fixes that by making every service a container: an isolated app with its own filesystem and dependencies, described by a file you can read, version, and re-run on a fresh machine. It's the difference between a server you administer and a server you declare.

The Mental Model

  • Image — the recipe: OS, runtime, app, baked in.
  • Container — one running instance of an image. Start, stop, throw away, start again.
  • Compose file — the whole service in text: which image, which ports, which folders hold its data.

That last one is the trick. A service stops being a sequence of install commands and becomes a small text file you keep in git.

One Service, One Compose File

A service lives in its own folder with a compose.yaml. Mine look like this:

services:
  web:
    image: my-app:latest
    ports:
      - "7700:7700"
    volumes:
      - ./data:/app/data        # data lives OUTSIDE the container
    restart: unless-stopped

And that's the whole deployment:

docker compose up -d        # start (build or pull first if needed)
docker compose ps           # is it running?
docker compose logs -f      # what is it saying?
docker compose down         # stop and remove

Re-running up -d after an edit is idempotent: Compose figures out what changed and recreates only what needs it. There's no "reinstall everything and hope."

Data Lives Outside the Container

Containers are disposable — that's their strength and their trap. Anything you care about must be on a volume or bind mount on the host, never inside the container's own filesystem. A container can be deleted and recreated at will; the folder on your disk is what survives.

volumes:
  - ./data:/app/data

This is also what makes backups sane: back up the data folders, not the containers.

Why One Server Can Run Twenty Services

Each container brings its own dependencies, so nothing fights over the host's runtime. A broken container is stopped and removed — it never drags the host or its neighbors down with it. And a fresh box isn't a rebuild, it's a restore: git clone the compose files, point them at the data, docker compose up -d. Done.

Updates and the Honest Limits

docker compose pull          # fetch newer images
docker compose up -d         # recreate with them

Three honest caveats, because self-hosting is still hosting:

  • Containers aren't a firewall. A port you publish is a port on the internet. Publish only what must be public; keep the rest on your private tailnet (see the Tailscale post).
  • The host still needs patching. Containers isolate apps; they don't patch the kernel underneath them.
  • Disks fill. Logs and images grow without asking. Watch disk space, and prune images you're not running.
