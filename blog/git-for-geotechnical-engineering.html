Git for Geotechnical Engineering: Version Control That Survives a Project

August 2, 2026 · Heston Norcott, E.I.

Geotechnical deliverables are a revision problem wearing an engineering costume. A boring log gets corrected, a bearing capacity calc changes with a revised groundwater elevation, and suddenly the report is "Final_Rev3_FINAL_v2.docx." Then the client asks which version matches the stamped set — and nobody can answer.

Git exists to make that question impossible to ask. This is the workflow I use for geotech work: one repo per project, branch for revisions, tag every stamped deliverable, and never lose the pair between the data and the figure. It's not a developer habit bolted onto engineering — it's the audit trail your QA should already be demanding.

One Repo Per Project

A project is a natural unit: the borings, the lab data, the analysis, the figures, and the report all change together and get reviewed together. Put them in one repo so a commit is always a complete, reviewable state of the whole project.

cd ~/projects/hotel-parcel-17
git init
git add .
git commit -m "Initial: borings, lab data, and report skeleton"

Commit Like You'll Defend It in a Lawsuit

Every commit should be one logical change, with a message that names the data and the action. Six months later, git log is your memory — make it legible.

git add boring-logs/BH-01.csv
git commit -m "Add SPT data for BH-01"

git add analysis/settlement.py settlement.xlsx
git commit -m "Fix settlement calc: use measured GW depth, not assumed"

Atomic commits matter here more than in software: when a figure and a calculation disagree later, you want to be able to isolate exactly which change introduced the difference.

Branch for a Revision, Tag for a Stamp

When the review comes back, don't edit in place. Make a branch for the revision so the submitted set stays intact and untouched, and keep working forward.

git checkout -b rev-02
# ...address reviewer comments, commit as you go...

And the one habit I'd push hardest: tag the exact commit you stamped and submitted. A tag is a bookmark you can return to forever — the reproduction of what left your desk.

git tag stamped-2026-08-01
git push origin stamped-2026-08-01

When the client asks "which version did we review?" the answer is a tag name, not a folder full of FINAL_v2 files.

Never Lose the Data-Figure Pair

The figure must always be reproducible from the numbers. Keep the CSV/GeoJSON and the script that made the figure in the same repo, and the figure becomes a derived artifact instead of a hand-edited drawing.

git diff analysis/settlement.py          # what changed in the calc
git blame boring-logs/BH-01.csv | head  # who entered which SPT value, line by line

Undoing Mistakes (Without Panic)

The commands that rescue you when a file goes sideways — and none of them require you to have made a backup:

git restore analysis/settlement.py        # discard edits, keep history
git stash                                 # park half-done work, clean tree
git stash pop                             # bring it back
git revert <commit>                       # safe undo: a new commit that un-does one
git log --oneline --all                   # find the state you want

Push to a Private Remote

Client data belongs in a private repository — GitHub/GitLab private repos are free, and the remote doubles as an off-site backup. This site's repo is public; every project repo stays private.

git remote add origin git@github.com:you/hotel-parcel-17.git
git push -u origin main
git pull

Keep Binaries Out, Keep Data In

A .gitignore tells git what never belongs in the repo. For geotech: generated files, giant rasters, and anything reproducible. In: CSVs, GeoJSON, scripts, and the final PDF.

.venv/
*.tif
*.bak
__pycache__/
report-output/

The One Workflow to Adopt

Everything that leaves your desk is tagged. Every change is a commit with a legible message. Every figure is reproducible from the data beside it. That's not overhead — that's the audit trail your discipline deserves, and it costs nothing but good habits.
